# 插件系统开放性分析：从「按功能枚举」到「按机制组合」

> **触发**：2026-10-21，用户让第三方插件（独立仓库 `ST-Manager-AI-Assistant`）把 AI 助手在右键菜单、批量菜单里的入口折叠成二级菜单，插件侧代码必须等宿主 commit `2610ba5` 才能生效。用户由此判断：插件系统不够开放，第三方插件想做新功能经常必须等宿主适配，要求整体分析改进方向。
>
> **性质**：只读分析稿，不含实施。证据基线：宿主 HEAD `4654e31`、插件 HEAD `8cefb92`。
> **状态**：已拍板。设计定稿见 `docs/2026-10-21-plugin-contract-v3-design.md`（决策记录 `docs/adr/0001`–`0016`）；本文保留为问题分析记录，§8 的候选方案以定稿设计为准。

---

## 0. 一句话结论

插件系统**不缺能力，缺的是「表达宿主 UI 结构」的通用机制**。

- 能力面已经相当开放：后端 15 个域 / 63 个域方法、前端 30 个顶层成员，路由、作业、CLI、静态资产、自定义事件都真正可用（`docs/plugin-api.md:9`）。
- 真正封闭的是**声明面与呈现面**：入口字段、入口种类、落点、菜单结构、容器类型、层叠位置，全部由宿主以「功能枚举」的方式写死在代码与模板里。插件每需要一种新的界面形态，宿主就必须新增一个特例。
- 二级菜单事件是这条路径依赖的典型样本：**契约层只增加了 5 行，呈现层却要重写约 1,000 行、5 个测试文件与 2 份文档**；而同一需求在两天前刚被宿主文档以「为一个插件加特性不划算」拒绝（`docs/2026-10-19-host-patch.md:385`）。
- 改进方向不是「拆掉宿主容器」（那会牺牲一致性、层级、移动端与安全边界），而是把扩展边界从「宿主有哪些 UI 功能」上移到「宿主有哪些通用组合机制」：**声明式贡献树 + 命名插槽 + 机器可读契约 + 通用呈现原语 + 受控的自定义通道**，并让宿主自己先用这套机制（dogfooding）。
- 时机关键：插件系统尚未公开发布，只有两个自研插件，`api_version` 还没有真正的兼容分支（`core/version.py:11-15`）。**这是最后一次低成本的契约塑形窗口**；发布后再做，代价会变成破坏第三方插件。

## 1. 起因复盘：二级菜单为什么必须改宿主

### 1.1 事实时间线

| 时间 | 事件 | 证据 |
|---|---|---|
| 2026-10-19 | 插件侧提出 6 条宿主补丁需求，其中「入口二级子菜单（按插件分组）」被宿主明确拒绝。拒绝理由：**「当前插件 4 条右键入口，全宿主最多也就十几条；宿主现有 `entries[]` 契约没有 `parent`/`group` 字段，为一个插件加特性不划算」** | `docs/2026-10-19-host-patch.md:385` |
| 同日 | 插件侧重构文档已计划把入口从 4 条扩到 12 条 | 插件仓库 `docs/2026-10-19-task-centric-redesign.md` |
| 2026-10-21 | 用户提出菜单被 7 条入口占满；宿主实现 `group` 字段，右键/批量菜单折叠为二级浮层 | 宿主 `2610ba5`（22 文件，+2248/−254）；插件 `8cefb92` |

拒绝所依据的「当前只有 4 条入口」是一个**会立刻过期的快照**；而需求本身没有变。这说明缺的不是判断力，而是**准入机制**：没有一条规则回答「什么样的插件诉求应当被通用化、什么样的应当被拒绝、拒绝后如何复审」。

### 1.2 成本结构：契约很便宜，呈现很贵

`2610ba5` 中真正直接服务于 `group` 的改动（注：同一 commit 还夹带了插件侧 host-patch §1–§6 的落地，如 `host.selection()`、`worldbook.sources()`、命令面板过滤，因此总行数不是纯 `group` 成本）：

| 层 | 改动 | 量级 |
|---|---|---|
| **声明契约** | `core/plugins/entries.py`：`KNOWN_ENTRY_KEYS` 加 `group` + 规范化透传 | **+5 行** |
| 注册表派生 | `static/js/entryRegistry.js`：`menuGroups()`（入口列表 → 渲染单元，含 `group` 折叠、`enabledOnly` 过滤） | +62 行 |
| 两套菜单实现 | `static/js/components/contextMenu.js`（右键）+ `header.js`（批量）各自加父项/子项/开关/Escape/滚动关闭/锚点重试 | 约 +400 行 |
| 两套模板 | `templates/components/context_menu.html` + `header.html`（桌面菜单 + 移动端第二屏 / 移动端选中栏） | 约 +220 行 |
| 浮层定位 | 新建 `static/js/utils/flyoutPosition.js`（锚点归一化、渲染后测量、放不下整体上移） | +143 行 |
| 层级/包含块 | `ui-refresh.css`：`.header-bar` 的 `backdrop-filter` 造包含块，必须 teleport 到 body + 提高 z-index | +94 行 |
| 文档 | `host-patch.md` +400 行、设计文档、API 文档/生成器 | 约 +415 行 |
| 测试 | 5 个测试文件，直接钉模板字符串与渲染分支 | +563 行 |

**比值约 200:1（呈现 : 契约）**。而且这不是第一次：新增 `batch` kind 是 19 文件 +1226/−88（`ea57806`）；新增 `ambient` surface + 核心事件 SSE 是 31 文件 +5475/−61（`29aa4f4`）。**声明层每加一个语义，宿主就要重建一遍整条渲染管道。**

### 1.3 它暴露的不是一个字段，而是一个模型

`group` 的两天反转说明三件事：

1. **封闭点在「声明空间」而不是「能力空间」。** 插件能自己写路由、跑作业、注册 CLI、发自定义事件；但想在宿主菜单里多一层结构，只能等宿主。
2. **同一份 `entries[]` 在宿主有多个各自为政的消费点。** 右键菜单（桌面/移动端第二屏）、批量菜单（桌面/移动端选中栏）、命令面板、入口坞，各有自己的模板与状态机。`group` 只在其中两个菜单生效，在 `dock`/`command` 里声明 `group` 是静默无效的——插件无法从契约预测声明结果。
3. **契约变更的「前向兼容」是缺失的。** 入口未知子键现在会导致**整个插件拒绝加载**（`core/plugins/manifest.py:613-628`，`code='manifest_unknown_key'`），而不是忽略 + 警告。插件侧的应对是在自己的测试里**复刻宿主的白名单**（插件仓库 `tests/test_manifest_contract.py`，commit `8cefb92` 描述原文：「漏了会拒绝加载整个插件」）；类似地它还复刻了 `evaluateWhen` 与 CSS 作用域扫描器。**第三方为了不静默消失，被迫维护三份宿主逻辑的副本。**

## 2. 现状诊断：开放性缺口分五层

| 层 | 现在已经开放的 | 缺口 | 典型症状 |
|---|---|---|---|
| **L1 声明层**（manifest 结构） | `entries[]` 的 16 个字段、`when` 条件、`config_schema`、`permissions` | 字段/枚举是封闭白名单；未知键**硬拒载**；新增字段 = 宿主改校验 + 前端消费 + 文档生成器 + 测试 | 加一个 `group` 要协调两个仓库发版 |
| **L2 呈现层**（宿主 UI 结构） | 入口 kind：`dock`/`nav`/`settings`/`context`/`command`/`status`/`batch`（实际有消费者 5 种） | 无菜单树/插槽/分区/分隔线概念；无「组角标/组图标」声明；同一 entries 多条渲染路径 | 二级菜单只能宿主实现；组角标靠宿主启发式求和 |
| **L3 容器层**（插件 UI 放在哪） | `surfaces.*` 5 种类型（panel/modal/page/sheet/ambient），容器归宿主，插件在 `mount(container)` 内自由 | 只覆盖「整块容器」，不覆盖「嵌入宿主已有 UI」（菜单项、header 动作区、卡片详情 tab、设置分区、空态、状态行） | 想放一个按钮到宿主 header，只能自绘 fixed 浮层（被反目标禁止） |
| **L4 能力层**（数据与动作） | 15 域 63 方法；`host.onState`/`host.selection`；`ui.*` 18 个原语；SSE 核心事件；`storage.*` | 前端仍缺结构性原语（menu/popover/tabs/layout）；少量数据仍靠读 `store`；`config_schema` 只支持标量子集（array/object 被拒） | 插件 `plugin.css` 从 784 行涨到 1255 行，重画宿主已存在的面板/表单/状态 |
| **L5 契约与治理** | 生成式 API 文档、46 个契约测试、`api_version=2` 支持 `(2,1)`、稳定性分级、tier 准入、活体夹具 `hello-world` | 设计文档已过时（仍列已删除的 `db()`/`suppress_fs_events()`）；`api_version` 无真实兼容分支；无机器可读 schema；无第三方自测工具；拒绝决策无记录（`docs/adr/` 目录不存在） | 第三方照设计文档写会踩空；插件复刻宿主逻辑；「拒绝 → 两天后实现」无据可查 |

**一句话诊断**：**L4 能力层已经「放开能力、机制内部化」；L1/L2/L3 却仍是「宿主枚举功能、插件填表」**。插件系统的开放程度因此取决于宿主 UI 的种类数，而不是机制的表达力。

## 3. 根因：为什么会形成「加特例」的路径依赖

### 3.1 扩展模型是 feature-first，而不是 mechanism-first

现有契约把「插件想做的事」直接映射成宿主功能：7 种 entry kind、5 种 surface type、16 个 entry 字段、11 个核心事件名……每个值都对应一段宿主专属渲染/处理代码。于是：

- 新需求 → 新枚举值 → 新渲染分支 → 新测试/文档；
- 旧枚举值无法组合（`group` 只对两个菜单生效；`when.target: card` 因为宿主没有卡片级右键而成为死代码）；
- 能力增长是线性的，宿主代码量也是线性的。

如果契约的单位是**机制**（贡献树、插槽、动作、条件、数据 API），新需求大多是「已有机制的新数据」，宿主代码不增长。这是 VS Code、Obsidian 这类成熟插件体系的分界点：它们的菜单项/面板/命令不是宿主逐个实现的，而是统一贡献注册表 + 统一渲染器。

### 3.2 「容器归宿主」不变量只覆盖了 surface 内部

设计文档明确：`插件不拥有容器；容器的一切由宿主负责；插件只往给定 container 里塞内容`（`docs/2026-09-22-plugin-system-design.md:1516-1518`，F14 :1679）。这条不变量本身是对的，它消灭了「插件自绘 fixed 浮层」的乱象。

但它只定义了**整块容器**（surface）的归属，没有定义**宿主自己 UI 里的嵌入点**。当插件想把一个按钮放进宿主 header、把一个 tab 放进卡片详情、把一个分组放进右键菜单时，契约没有对应物——插件要么挤进现有 kind，要么自绘（被禁止）。**不变量覆盖不到的地方，就是宿主必须改代码的地方。**

### 3.3 契约真相在宿主实现里，没有机器可读的声明契约

`entries` 白名单在 `core/plugins/entries.py`，前端镜像在 `entryRegistry.js`，可渲染 kind 在 `pluginManager.js`，文档由 `tools/gen_plugin_api_docs.py` 从代码生成，测试再断言文档与代码一致。这条链对**宿主自身回归**非常有效，但对第三方是三个问题：

1. **无法自测**：插件只能复刻白名单/`evaluateWhen`/CSS 扫描器，或者装进宿主试错；
2. **无法向前兼容**：宿主用「未知键拒载」保证严格性，代价是插件不能带任何宿主未实现的字段；
3. **真相会漂移**：设计文档 §10 仍列已删除的 `db()`/`suppress_fs_events()`/扁平 `read_card`，而实际契约是 `plugin-api.md` + 代码。第三方最需要的「单一事实来源」反而是最缺的。

### 3.4 双仓库发布耦合 + 否决机制非制度化

官方插件独立仓库（正确决策）意味着：插件的任何界面新形态都要求宿主先发版。`docs/2026-10-19-host-patch.md` 实际上已经是一份**事实上的 RFC**（目标契约 + 逐条降级 + 验收方式），但这个流程没有名字、没有状态、没有复审、没有 ADR。于是：

- 拒绝的理由会随快照过期（「当前只有 4 条入口」）；
- 同一需求被拒两天后又被实现，没有人需要解释；
- 插件只能维护「兼容降级层」等待宿主（本次事件中的 `frontend/scope.js`、`selection.js` 都是这么来的，补丁合入后删除）。

### 3.5 治理按「单作者高可靠」优化，抑制了增量演进

逐字文档断言、AST/反射一致性、源码子串断言、封闭枚举断言——这些测试保护了宿主不回归，但也让每次能力扩展变成 19~31 个文件、上千行的工程。再叠加「Stable 覆盖几乎全部 API」与「`api_version` 无行为分支」，实际效果是**契约接近冻结，任何新增都要走重流程**。对单人自研是质量保障，对第三方生态是准入摩擦。

## 4. 改进方向

### 4.0 目标与判定标准

开放性的目标不是「插件想干什么都行」，而是三条：

1. **可表达**：常见的新 UI/交互诉求，插件通过声明 + 现有机制就能完成，**零宿主改动**；
2. **可自测**：第三方不装宿主也能验证 manifest/CSS/API 用法是否符合契约；
3. **可演进**：宿主新增能力是纯增量；破坏性变更少且可预告；拒绝有记录、可复审。

对应的验收见 §6。以下方向按「机制 → 呈现 → 契约 → 治理」排列，D1/D2/D3 是核心。

---

### D1 贡献模型：用「菜单/动作树」替代「入口字段堆叠」

**问题**：入口是叶子节点，只有扁平字段；`group` 是为了让叶子能折叠成一层而加的特例，无法表达嵌套、分区、分隔、排序、动态子项、组级角标。

**做法**：把 `frontend.entries[]` 泛化为 `frontend.contributions`（entries 保留为一种兼容/语法糖），声明单位从「入口」变成「贡献节点树」：

```jsonc
// manifest.json（草案示意）
"frontend": {
  "contributions": {
    "menus": [
      {
        "placement": "context.folder",          // 宿主定义的命名落点
        "when": { "mode": ["cards"] },
        "title": "AI 助手",
        "icon": "frontend/assets/icon.svg",
        "order": 100,
        "children": [
          { "title": "分析此分类", "action": { "type": "surface", "id": "task" } },
          { "title": "打标此分类", "action": { "type": "surface", "id": "classify" } },
          { "type": "separator" },
          { "title": "更多", "children": [
            { "title": "打标设置", "action": { "type": "command", "id": "open-settings" } }
          ] }
        ]
      }
    ]
  }
}
```

要点：

- **节点类型只有几种**：`item` / `separator` / `section`（分组标题）；子节点即二级/三级菜单。
- **动作类型收敛为有限集合**：打开 surface、执行命令、派发事件、调用 `host.*`、打开 URL。宿主统一执行动作，插件不接触渲染。
- **条件与动态数据沿用现有机制**：`when` 在节点级求值；`badge`/`label`/`enabled` 通过 `api.entries.*` 的运行时 API 按 id 更新（组级角标由宿主按子项聚合规则算，或允许节点声明 `aggregate: 'sum'`）。
- **落点（placement）是宿主定义的命名空间**，不是插件自造的定位：`context.folder` / `context.card` / `batch.selection` / `commandPalette` / `dock` / `settings.nav` / `page.cards.toolbar` / `card.detail.tabs` / `empty.cards` / `context.footer` 等。宿主每新增一个落点，所有插件自动获得新位置。
- 旧 `entries[]` 在过渡期内被解析成等价的贡献树（`kind` → `placement` 映射），保证已有两个插件不需要立刻重写。

**收益**：`group`、嵌套、分隔线、排序、组级 badge、命令面板/坞/右键的同一份声明 —— 全部变成数据。宿主只需实现**一个递归菜单渲染器 + 一套动作执行器**，替代现在 `contextMenu.js` / `header.js` / `commandPalette.js` / 模板里的多套实现。

**代价**：一次性的 schema/渲染器重构；现有 5 个 kinds 与渲染路径需要合并。建议在发布前做。

**与现有约束的关系**：完全兼容 F13/F14——菜单仍由宿主渲染、宿主定位、宿主管理层级；插件只声明数据。

### D2 命名插槽：让「插件内容嵌入宿主 UI」成为数据

**问题**：`surfaces` 解决「整块容器」，但没有「宿主已有 UI 里的一个位置」。当前想往设置页、header、卡片详情、右键菜单底部加东西，只能改宿主模板。

**做法**：定义宿主**插槽注册表**（slot registry），插件用声明或运行时 API 往插槽里放「渲染器」或「贡献节点」：

```jsonc
"slots": [
  { "slot": "settings.section", "id": "ai-profiles", "title": "AI 助手档案",
    "mount": "frontend/views/settings.js#mountAiSection" },
  { "slot": "card.detail.tabs", "id": "ai-analysis", "title": "AI 分析",
    "render": "frontend/views/detailTab.js#mount" },
  { "slot": "context.footer", "contribution": "menus/ai-footer" }
]
```

插槽分两类：

1. **声明型插槽**（`contribution`）：只放贡献节点，宿主完全掌控渲染（适合菜单、命令、状态项）；
2. **渲染型插槽**（`mount`/`render`）：宿主提供**有边界的容器**（尺寸、滚动、主题、焦点、卸载），插件在容器内自由 DOM（适合设置分区、详情 tab、面板内容）。

宿主需要保证的契约与 surface 一致：容器归宿主、插件不得设置 `position`/`z-index`/`inset`、禁用/卸载时强制回收、`mount` 抛错隔离。

**首批插槽建议**（按证据中的高频诉求排序）：`settings.section`（已有雏形）、`page.*.toolbar`、`card.detail.tabs`、`context.footer`、`header.actions`、`empty.*`、`dock.overflow`、`statusBar`（如果决定实现 `status` kind）。

**收益**：把「加一个落点 = 改宿主模板」变成「加一个插槽声明」。插件不再需要自绘 fixed 浮层来挤进宿主 UI。

**代价**：宿主模板需要插入插槽锚点（一次性、有限数量）；插槽的布局/响应式由宿主负责（这正是它比自绘可靠的地方）。

---

### D3 机器可读契约：schema + 生成器 + 第三方自测 CLI

**问题**：白名单/枚举/渲染能力分散在 Python、前端 JS、生成器、文档、测试五处；未知键硬拒载；插件被迫复刻宿主逻辑。

**做法**：

1. **单一契约源**：用一份机器可读定义（JSON Schema / Python dataclass / 前端共享常量三选一，推荐 JSON Schema 为产物、代码为源）描述 manifest 全部结构：顶层键、`frontend.contributions` 节点类型、`when` 表达式、`config_schema`、`surface` spec、`slots`、权限与 tier 规则。
2. **由它生成**：宿主的校验器、`docs/plugin-api.md` 的结构部分、前端 `normalize` 的字段表、以及给第三方的 JSON Schema 文件/TS 类型。
3. **第三方工具链**：`stm-plugin-check` CLI（可 pip 安装或单文件分发）做四件事：manifest schema 校验、条目矩阵校验（`when`/kind/placement 组合是否合法）、CSS 作用域与令牌检查、对某个宿主版本的 API 使用检查。官方插件仓 CI 直接跑它；第三方也可以。
4. **前向兼容策略**：发布后，`entries`/`contributions` 的未知子键从「拒载」改为**警告 + 忽略 + UI 标记**（宿主 CI 可用 `--strict` 保持严格）；新增字段默认可选；删除/改名走 deprecation。这样插件可以先于宿主使用新字段并优雅降级，而不是整插件消失。
5. **活体夹具升级**：`samples/plugins/hello-world` 扩展为覆盖所有插槽/节点类型/动作类型的契约夹具；宿主 CI 用它证明契约可用，插件作者拿它当最小示例。

**收益**：消除三份复刻；宿主新增字段的成本从「改五处 + 测试」降为「改 schema + 渲染器一处」；第三方获得自测能力。

**代价**：一次性建立 schema 与生成管线；需要决定「schema 是源还是产物」（推荐代码为源、schema 为产物，避免手写漂移）。

### D4 通用呈现原语下沉：menu / popover / tabs / layout + 层叠契约

**问题**：本次事件里，浮层定位（`flyoutPosition.js`）、层叠上下文（`.header-bar` 的 `backdrop-filter`）、z-index 递增、移动端第二屏，全部是宿主内部逻辑。插件即使想在**自己的 surface 内**弹一个菜单，也只能自己算位置、猜层级。

**做法**：

- `api.ui` 增加结构性原语：`menu(items)`、`popover(anchor, content)`、`tabs(items)`、`section`、`toolbar`、`layout`/`grid`（部分已有）。**定位、翻转/夹取、层级、焦点、ESC、移动端降级由宿主实现**；插件只描述内容。
- 明确**层叠契约**：宿主定义一组命名层（content < ambient < surface < drawer < dock < dropdown/popover < tooltip < alert），插件通过 `api.ui.popover` 或插槽获得层级，不允许自己写 `z-index`。这比现在「按 surface type 猜层级」可靠，也能修复「插件 modal 声明 3400 却看不见」这类问题。
- 收敛渲染路径：把右键菜单、批量菜单、命令面板、坞溢出菜单统一到**一个数据驱动的菜单组件**（D1 的渲染器），移动端降级只实现一次。

**收益**：插件不需要理解宿主 CSS/层叠/定位；宿主改视觉或移动端时所有插件自动跟随。`plugin.css` 的重复外壳/表单/状态样式可以继续下降（原语库验收线：CSS 明显缩短，否则说明原语设计失败——这条判据来自 `2026-10-10-plugin-entry-unification-addendum.md` §4.1）。

### D5 受限的自定义通道：容器内自由，容器外受控

**问题**：不是所有新交互都能立刻抽象成通用插槽。如果坚持「先有宿主机制，插件才能做」，插件创新永远慢一个宿主版本；如果放开自绘，又会回到「球满天飞」/层级失控/无法卸载。

**做法**：提供一条**受控逃生舱**，同时保持 F13/F14：

- `surface.type: 'custom'` 或 `slot.renderer`：插件拥有容器**内部**的完整 DOM 自由，宿主只拥有外框（尺寸档位、定位、滚动、焦点陷阱、层级、卸载、错误隔离）。**不允许**插件定位容器本身（那正是 F13 禁止的东西）。
- 用能力声明 + 权限/tier 门控：`requires: ["ui.custom"]`，宿主在安装/启用时披露；实验性阶段可只对 official/verified 开放。
- **提级路径**：当同一种自定义形态被两个以上插件使用，就把它提升为宿主原语/插槽类型（并在文档里记录）。这要求宿主维护「自定义使用台账」，否则逃生舱会变成永久绕过。

**收益**：解除「等待宿主发版」的死锁；同时把自由度限制在宿主可控的边界内。插件可以先做，宿主择机收编。

**代价**：需要设计能力声明/披露与回收语义；要防止 custom 变成事实标准。

### D6 宿主自食其果（dogfooding）+ 扩展点准入流程（RFC / ADR）

**问题一**：宿主自己的 UI（右键菜单、批量栏、设置分区、坞）是手写的，插件的贡献路径自然也是手写的。只要宿主可以「直接改模板」，就没有动力把机制做通用。

**做法**：宿主自己的菜单项/入口/设置分区也通过**同一套贡献注册表**注册（宿主作为「core 插件」）。这样：

- 新宿主功能必须先用贡献机制表达，否则注册不进去；
- 契约活体夹具就是宿主自己；
- 「新 UI = 新宿主代码」的路径依赖被打破。

**问题二**：`host-patch.md` 已是事实 RFC，但没有状态与记录；拒绝理由会过期。**做法**：把它升格为正式流程：

1. 插件侧提交「扩展点申请」（目标契约 + 降级路径 + 影响面）；
2. 宿主按**分类树**裁决：数据/能力 → API；结构/呈现 → 贡献树或插槽；全新交互 → D5 受控通道；确实越界 → 拒绝并写入 ADR（`docs/adr/`，当前 AGENTS.md 声称存在但实际没有该目录）；
3. 拒绝必须给出**可验证、非快照性**的理由（例如「与信任模型冲突」，而不是「现在只有 4 条入口」）；
4. 建立**复审触发条件**（数量阈值、第二个插件提出、tier 变化）与定期回顾。

**收益**：把「宿主拍脑袋决定」变成可预期、可申诉、可追溯的机制；这也是用户感知「插件能不能自主完成」的制度来源。

### D7 运行时与生态配套（较小但必要的修补）

按优先级：

1. **`api_version` 名存实亡**：当前支持 `(2,1)` 但全仓没有按版本分支的代码（`core/version.py:11-15`；`core/plugins/manifest.py` 仅做白名单）。要么实现真正的兼容分支，要么把语义改成「宿主只保证当前版本」，并靠 `requires`/`when.feature` 做能力协商。**推荐**：新增 `requires.capabilities` 与 `when.capability`，插件声明依赖的机制（如 `menus.tree`、`slots.settings`），宿主据能力表降级；`api_version` 只在破坏性变更时升。
2. **安全小口子**：核心事件可被插件伪造（`core/plugins/api.py:227-234`，测试还明确断言允许）；`api.private.query` 可读任意表（含其他插件作业表，`core/plugins/domains/private.py:80-124`）；后端插件本身是进程内任意 Python（无沙箱，设计 D7）。在「打开声明面」之前建议先堵前两个，避免把开放与越权混在一起。
3. **跨插件组合**：设计文档说允许跨插件事件订阅（N1），实现上后端 `hooks.register` 强制 `<own_id>:` 前缀、跨插件订阅被阻断（`core/plugins/hooks.py:111-113`），前端又只走 window（不进 SSE）。生态若要「插件互相组合」，需要先明确定位：允许事件订阅（best-effort）但不提供调用；并把这个边界写进文档。
4. **`config_schema` 扩展**：结构化配置（array/object/动态选项）目前被拒，导致插件自建设置页，与宿主配置面永久分叉（反目标 11「不允许插件自建设置模态」因此无法执行）。建议增加 `array`/`object`/`x-ui: custom`，把「自定义」收进宿主设置容器。
5. **`nav`/`status` 的取舍**：枚举里有、无消费者、社区被 tier 禁止。要么实现（宿主提供侧栏「插件」入口 / 状态栏区域），要么从契约里删掉，避免「声明了但永远不出现」的静默失败。

## 5. 落地顺序建议

> 前提：插件系统未公开发布、只有两个自研插件、`api_version` 无真实兼容负担——**现在是窗口期**。

### P0（发布前必须做，决定生态上限）

1. **D1 贡献树 + 统一菜单渲染器**（右键/批量/命令面板/坞先接入）；`entries[]` 解析为贡献树的兼容层。
2. **D2 首批命名插槽**（`settings.section`、`page.*.toolbar`、`card.detail.tabs`、`context.footer`、`header.actions`）。
3. **D3 契约 schema 化 + `stm-plugin-check` + 活体夹具升级 + 前向兼容策略**（未知键 warning，宿主 CI 用 strict）。
4. **D6 流程轻量版**：host-patch → RFC 模板 + 决策记录目录（ADR）+ 拒绝理由规范。
5. 修复文档漂移：设计文档 §10 的已删 API 清单、`group` 进 entries 字段表；明确 `plugin-api.md` 是 API 唯一真相。

### P1（紧随其后）

6. **D4 结构性原语**（menu/popover/tabs/layout）+ 层叠契约；`plugin.css` 瘦身验收。
7. **D5 受控自定义通道** + 能力声明/tier 门控 + 提级台账。
8. **D6 dogfooding**：宿主菜单/设置分区迁到贡献注册表（可与新功能并行，逐步替换）。
9. **D7 版本与能力协商**、核心事件伪造/跨表读两个安全修补。

### P2（生态化）

10. 后端服务能力的继续投影（chats/presets/extensions 写操作、通用 token 估算等）。
11. 契约兼容矩阵 CI（宿主版本 × 官方插件版本）、官方插件模板仓、第三方契约测试模板。
12. 跨插件组合策略定稿（事件订阅、组件复用、插件间调用是否开放）。

## 7. 与现有设计约束的关系

**保留（不变量）**：

- 容器归宿主（F14），插件只能在 container 内创建 DOM；禁止自绘 `position: fixed` 浮层（F13/F16）——D1/D2/D4 都是在这条边界**内部**增加表达力。
- CSS 作用域（F11）、令牌契约（F15）、资产扩展名与 CSP、路径 realpath、`ui_data` 命名空间与配额、密钥隔离。
- 不提供插件间调用 API（N1），但跨插件事件订阅要明确为 best-effort 并写清文档（当前实现与文档不一致，需修正）。
- 无沙箱（D7）：本地单用户工具，插件是可信/半可信代码；权限/tier 是披露与风险分级，不是安全边界——文档应避免用「封闭枚举」暗示安全性。

**需要重审**：

- 「不允许插件自建设置模态」在 `config_schema` 不支持结构化配置时无法执行；要么扩展 schema（推荐），要么删除该反目标。
- 「社区插件不得使用 `nav`/`status`」是产品决策，但当前实现是「枚举存在、永远不渲染」，应改为「tier 不允许时不接受该 kind 声明并明确报错」，避免静默失败。
- 「拒绝理由基于当前使用量」（host-patch §7）不成立：使用量是快照，应改用「机制分类 + 复审触发条件」。

**明确不做**：

- 不做浏览器 iframe/沙箱隔离（本地单用户，成本 > 收益）。
- 不开放「插件自绘容器外浮层」。
- 不提供插件间直接调用。

## 8. 需要拍板的问题

1. **发布前是否做一次契约重塑？**（推荐：是。把 D1/D2/D3 作为「生态契约 v1」一次成型；`api_version` 升 3 只对内部两个插件做迁移。）
2. **是否接受宿主 UI 走贡献注册表（dogfooding）？** 这是长期开放性的最高杠杆，但会动宿主模板/菜单实现，工作量最大。
3. **受控自定义通道（D5）是否开放？** 开放到什么 tier/权限？如果不开放，插件遇到新交互形态仍只能等宿主，需要接受这一点并写进契约。
4. **跨插件组合是否作为生态目标？** 若是，需重写 N1 与 hooks 实现（后端事件桥、组件复用边界）；若不是，删掉文档中的「允许跨插件订阅」承诺。
5. **是否建立 `docs/adr/` 与 RFC 流程？** AGENTS.md 已声称 ADR 在 `docs/adr/`，但目录不存在；建议补上并记录本次「拒绝 → 反转」的决策。
6. **`api_version` 语义**：真正的多版本兼容分支，还是「只保证当前版本 + 能力协商」？（推荐后者，成本低且足够。）
